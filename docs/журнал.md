## Шаг 3. Регистрация

11 октября 2026

Появилась регистрация. Вход, обновление токена и профиль будут следующим шагом.

- `POST /api/v1/auth/register` создаёт пользователя и сразу возвращает сессию: access token на 15 минут и refresh token на 30 суток.
- Почта обрезается и приводится к нижнему регистру. Повторная почта отвечает `409 email_taken`.
- Пароль хранится только как хэш. Пробелы по краям пароля сохраняются.
- Часовой пояс по умолчанию — `Europe/Moscow`. Неизвестный пояс отвечает `422 validation_error` с кодом поля `invalid_timezone`.
- Секрет подписи токена читается из `JWT_SECRET`. Локальное значение по умолчанию подходит для разработки.

Проверка:

```bash
docker compose up --build -d
uv run alembic upgrade head
uv run pytest
```

Пример запроса:

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com","password":"password1"}'
```

## Шаг 4. Сессия

11 октября 2026

Появились вход, обновление токена, выход и профиль.

- `POST /api/v1/auth/login` возвращает новую сессию. Неизвестная почта и неверный пароль отвечают одинаково: `401 invalid_credentials`.
- Больше 10 попыток входа в минуту с одного адреса отвечает `429 too_many_requests`.
- `POST /api/v1/auth/refresh` выдаёт новую пару токенов. Прежний refresh token после этого не действует. Просроченный и неизвестный отвечают `401 invalid_refresh`.
- `POST /api/v1/auth/logout` отзывает refresh token и отвечает `204`. Повторный выход тоже отвечает `204`. Уже выданный access token действует до своего срока.
- `GET /api/v1/auth/me` и `PATCH /api/v1/auth/me` требуют access token. Просроченный токен отвечает `401 token_expired`, отсутствующий или испорченный — `401 unauthorized`.
- Смена пояса меняет только отображение времени. Сохранённый момент создания пользователя остаётся тем же.

Проверка:

```bash
uv run pytest
```

## Шаг 5. Задачи: создание и списки

11 октября 2026

Появились задачи. Описание обязательно, срок необязателен.

- `POST /api/v1/tasks` создаёт задачу в статусе `active`. Ответ `201`, заголовок `Location` ведёт на созданную задачу.
- Срок — календарная дата в поясе пользователя. Сегодняшний день допустим, вчерашний отвечает `422 in_the_past` и запись не создаётся.
- `GET /api/v1/tasks` возвращает задачи владельца, в том числе без срока. Чужая задача в списке не появляется, а запрос по её идентификатору отвечает `404 not_found`.
- Фильтры: `status` (`active`, `completed`, `all`), `due` (`any`, `dated`, `undated`), период `from` и `to` включительно. Одна граница без другой или период вместе с `due=undated` отвечают `422 validation_error`. В выборке за период задач без срока нет.
- Порядок: сначала активные, затем выполненные; внутри группы срок по возрастанию, без срока в конце; при равенстве — по времени создания.

Проверка:

```bash
uv run alembic upgrade head
uv run pytest
```

## Шаг 6. Задачи: правка, выполнение и удаление

11 октября 2026

Задачу можно довести до конца: поправить, выполнить, вернуть в работу и удалить.

- `PATCH /api/v1/tasks/{id}` меняет только переданные `description` и `due_on`. `due_on: null` снимает срок. Новый срок в прошлом отвечает `422 in_the_past`, и задача остаётся прежней. Статус этим методом не меняется.
- `POST /api/v1/tasks/{id}/complete` переводит задачу в `completed`. Повтор отвечает `200` и `status_changed: false`, момент выполнения не сдвигается.
- `POST /api/v1/tasks/{id}/reopen` возвращает задачу в `active` и очищает `completed_at`. Срок при этом не проверяется, даже если он уже прошёл.
- `DELETE /api/v1/tasks/{id}` отвечает `204`. Повтор без ключа, когда записи уже нет, отвечает `404 not_found`.
- Заголовок `Idempotency-Key` на создании и удалении действует сутки и привязан к пользователю, методу и пути. Тот же ключ и то же тело возвращают прежний ответ. Тот же ключ с другим телом отвечает `409 idempotency_conflict`.

Проверка:

```bash
uv run alembic upgrade head
uv run pytest
```

## Шаг 7. Встречи: создание и списки

11 октября 2026

Появились встречи. У встречи всегда есть конец: если его не прислали, сервер ставит начало плюс один час.

- `POST /api/v1/meetings` отвечает `201` и телом `{meeting, overlaps}`. Заголовок `Location` ведёт на созданную встречу.
- Начало в прошлом, с допуском 60 секунд, отвечает `422 in_the_past`. Конец не позже начала отвечает `invalid_interval`. Длительность больше 24 часов отвечает `duration_too_long`. Ровно 24 часа допустимы.
- Пересечение полуоткрытое: встреча до 14:00 и встреча с 14:00 друг другу не мешают. Без `allow_overlap` сервер ничего не записывает и отвечает `409 overlap` со списком конфликтов. С `allow_overlap: true` встреча сохраняется, а в `overlaps` лежат текущие пересечения.
- `GET /api/v1/meetings` принимает период `from` и `to` парой календарных дат. Окно — от 00:00 даты `from` до конца даты `to` в поясе пользователя. В него входит встреча, чей интервал хоть немного задевает окно. Порядок — по началу, затем по id.

Проверка:

```bash
uv run alembic upgrade head
uv run pytest
```
